01

Choice gate

First decision the user makes. The bundled pet is pre-selected so the lazy path is one click; the custom path is given equal visual weight but with honest cost/time framing.

  • "~8 min · 8 image gens" sets expectations up-front. The current spec's "5-min target" is a lie; this one isn't.
  • "You can hatch additional pets later" defuses the FOMO of having to commit at first launch.
  • No mention of Codex auth here — it's already required to launch the app, so it's solved by the time we get here.
UX bet: framing this as a normal product onboarding choice, not a power-user feature buried in settings, is the difference between "people use it" and "people don't know it exists."

03

The only conversational moment.

This is the one place Codex output is user-facing — and it's framed as review the prompts we wrote, not chat with Codex. Each row is a discrete editable text field, not a streaming chat bubble.

  • Italic Fraunces for prompt text reads as "draft, work-in-progress copy" — invites editing rather than feeling final.
  • Row 03 (running-left) visibly marked as derived, mirrored from row 02. No separate generation, no separate prompt — matches what derive_running_left_from_running_right.py already does.
  • 9 rows shown · 8 prompts to generate — and the canonical row names (idle, running-right…review) come straight from the existing Python contract.
Why this step exists: the per-row prompts are the entire creative quality of the output. The original spec hand-waved them; making them visible-and-editable is what lets advanced users tune the result and gives novice users a sense of agency.

04

Pipeline view, not chat.

This is the screen the original chat-bubble UX would have ruined. Codex output never appears as a chat message — it manifests as state changes on the pipeline nodes and terse log lines in the runtime feed.

  • Sequential dependency rendering. Base anchors first; downstream rows show "grounded on base" so the user can see why identity stays consistent.
  • Mirror node is visually distinct (dashed, hatched) to signal "this isn't a generation step."
  • Per-row "Replace" lets users regenerate without restarting the run. Re-running an upstream node invalidates downstream ones — the UI handles this, not the user.
  • The runtime feed is technical, not conversational. Mono font, terse, log-shaped. Power users can read it; everyone else can ignore it.
  • Generation count is honest. "12 total imagegen calls" includes regens. Surfaces cost reality.
The structural insight: Codex's app-server protocol gives us image_generation_call events, file paths, and statuses. The wizard reads those events and updates pipeline state — there is literally no place a "chat bubble" would attach.

05

Validation is visual.

The atlas grid is the validation surface. Bad cells are marked in terracotta directly on the grid; good cells are olive; transparent unused cells render as a hatch pattern. No wall of text.

  • Row chip palette mirrors the cell colors. A failed row's chip turns terracotta — the eye can't miss which row to look at.
  • The mirrored row is visibly amber to signal "this came from row 02, not from a separate generation." Helps users understand what they're looking at.
  • Validation messages are specific and actionable — "Row 6 frame 3 has alpha noise" with a single-row regenerate button, not a generic "validation failed."
  • The technical specs (1536×1872 etc.) are mono-font checklist items, not a buried tooltip. Aimed at people who want to see them; ignorable for those who don't.
The atlas is the contract. Showing it directly, with the grid, makes the contract visible to the user instead of hidden inside a Rust validator. If we ever change what a valid atlas looks like, this screen is where we'd see the implications first.

06

Land back in the regular app.

The wizard ends with a single decision: activate now, or save for later. Either choice resolves into the normal app surface — pet window appears, library updated, wizard window closes.

  • Real timing data ("7 minutes 42 seconds, 12 generations") makes the cost of hatching legible after the fact. Sets honest expectations for the next pet.
  • Active-pet toggle is a soft default. Most people who just hatched a pet want to use it; the alternative is "save for the library and stick with what was active."
  • The package path footnote is for power users who want to know where the bytes live. Ignorable.
What's deliberately not here: no "share your pet" button, no community gallery, no rating prompt. The first hatching experience ends in using your pet, not in another decision.
